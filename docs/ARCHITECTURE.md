# Архитектура Async Job Hunter

## Цель

Async Job Hunter периодически получает вакансии из внешних источников, сохраняет
новые вакансии, показывает их в веб-интерфейсе и отправляет уведомления.
Приложение служит практикой модульной Clean Architecture, `thesis/dic`, Amp,
PostgreSQL и событийного взаимодействия модулей.

Первый результат должен быть полезным приложением, а не универсальной платформой.
Новые абстракции добавляются только для подтверждённого сценария.

## Слои и границы

Каждый модуль использует следующую структуру. Пустые директории не создаются.

- `Domain` публикует DTO, value objects, события и контракты модуля.
- `Application` реализует use cases и использует Domain своего модуля.
- `Infrastructure` реализует Domain-контракты и адаптирует внешние системы.
- `Presentation` содержит HTTP- и CLI-входы, конфигурацию и DI-модуль.

| Слой | Может использовать |
| --- | --- |
| `Presentation` | `Infrastructure` и `Application` своего модуля; `Domain` своего и других модулей |
| `Infrastructure` | `Application` своего модуля; `Domain` своего и других модулей |
| `Application` | `Application` и `Domain` своего модуля |
| `Domain` | `Domain` своего и других модулей |

Модули взаимодействуют через опубликованные Domain-события или через явно
экспортированный Domain-контракт. Внутри одного слоя интерфейс не создаётся без
практической причины.

## Модули первого инкремента

### `VacancyDiscovery`

Находит вакансии во внешних источниках и определяет, является ли вакансия новой.

- `VacancySource` абстрагирует источник; HH.ru является адаптером
  `Infrastructure/Hh`, а не частью Domain-модели.
- Внешняя вакансия идентифицируется парой `source` и `externalVacancyId`.
- Модуль владеет дедупликацией и после успешного обнаружения публикует
  `VacancyDiscovered`.
- Поиск по нескольким областям и запрос деталей выполняются конкурентно с
  ограничением параллелизма.

### `VacancyCatalog`

Владеет проекцией вакансий для пользователя.

- Подписывается на `VacancyDiscovered`.
- Сохраняет данные, необходимые для списка, карточки и фильтрации.
- Предоставляет use cases чтения.
- HTTP-контроллеры и HTML-view находятся в `Presentation/Http` этого модуля.

### `Notifications`

Отправляет уведомления о новых вакансиях и владеет состоянием их доставки.

- Подписывается на `VacancyDiscovered`.
- Хранит идентификатор вакансии, канал, статус, количество попыток и время
  отправки либо ошибки.
- Telegram является адаптером `Infrastructure/Telegram`.
- Повторная отправка реализуется отдельным use case, а не повторным поиском.

### `EventStore`

Технический модуль для неизменяемого журнала доменных событий.

- Событие содержит идентификатор, имя потока, тип, `occurred_at` в UTC и JSON
  payload.
- Контракт поддерживает добавление события и чтение истории потока.
- Хранилище реализуется через PostgreSQL и миграции.

Наличие `EventStore` не означает полный Event Sourcing: прикладные модули могут
владеть обычными проекциями и не обязаны восстанавливать агрегаты из истории.

### `EventBus`

Технический модуль доставляет Domain-события подписчикам.

- Перед публикацией событие неизменно добавляется в `EventStore`.
- В первом шаге `InMemoryEventBus` запускает каждый подходящий подписчик через
  `Amp\async()`. Ошибка одного обработчика логируется и не отменяет остальных.
- Доставка process-local и best-effort: событие, сохранённое перед аварией, но
  не обработанное подписчиком, не доставляется автоматически после рестарта.
- При появлении требования к надёжной доставке `InMemoryEventBus` заменяется
  PGMQ-ориентированной реализацией на основе `thesis/message-bus`. Контракты
  `EventBus` и `EventSubscriber` прикладных модулей при этом сохраняются.

### `Migration`

Технический модуль собирает миграции, экспортированные прикладными и
техническими модулями, проверяет уникальность версий и последовательно применяет
их к PostgreSQL. Прикладные таблицы создаются только миграциями.

## PostgreSQL и PGMQ

PostgreSQL является единственным runtime-хранилищем приложения. Он обслуживает
события, проекции каталога, дедупликацию, состояние доставок и журнал миграций.

- Доступ через PDO требует расширения `pdo_pgsql`.
- Короткие транзакции допускаются в адаптерах; долгую обработку нельзя держать
  внутри транзакции.
- JSON payload событий хранится в `jsonb`.
- PGMQ включается миграцией окружения `CREATE EXTENSION IF NOT EXISTS pgmq`.
- `thesis/postgres` не используется: пакет архивирован.

## HTTP и CLI

`amphp/http-server` обслуживает веб-интерфейс, а
`amphp/http-server-router` маршрутизирует запросы. Долгоживущий HTTP-сервер
получает `Scoped<T>` обработчик, чтобы request-зависимости создавались и
освобождались в пределах одного запроса.

CLI-точки входа остаются тонкими bootstrap-скриптами. Daemon последовательно
запускает поиск и неблокирующе ждёт интервал через `Amp\delay()`. `SIGINT` и
`SIGTERM` останавливают следующий цикл, не прерывая уже начатую обработку.

## DIC и composition root

`MigrateModule` является composition root. Он импортирует модули и передаёт между
ними только типизированные `Ref<T>` exports. Корневой модуль не знает деталей
PDO, PGMQ, HTTP-клиента источника или Telegram.

Регистрация остаётся явной через `object()` и `arg()`. Autowiring, tags и
autoconfiguration добавляются только после появления подтверждённого boilerplate.

## Конфиденциальные данные

Пароли PostgreSQL, токены источников и Telegram читаются только в
`Presentation/Config` из окружения. Они не попадают в код, документацию или
логи.

## Тестирование

- Unit: отбор вакансий, дедупликация, форматирование уведомлений.
- Integration: PostgreSQL-адаптеры, миграции, EventStore и проекции.
- Integration: HTTP-контроллеры с test-адаптерами и request scope.
- End-to-end: поиск, публикация события, каталог и уведомление без реальных
  источников и Telegram.
- Architecture: направления зависимостей между слоями и модулями.

Тесты не зависят от реальной сети, секретов или времени суток.

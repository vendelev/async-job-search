# Осознанные архитектурные компромиссы

Для упрощения реализации и ускорения разработки приняты следующие компромиссы относительно строгих принципов Clean Architecture и CQRS.

## Eloquent модели в Domain слое

### Стандарт Clean Architecture

ORM-модели, например Eloquent, должны располагаться в Infrastructure слое, так как они представляют технические детали доступа к данным.

### Наше решение

Eloquent-модели располагаются в `Domain/Entity`.

```php
namespace App\Currency\Domain\Entity;

use Illuminate\Database\Eloquent\Model;

class CurrencyConversion extends Model
{
    // ...
}
```

### Почему принято это решение

1. Упрощение: не нужно создавать отдельные классы для Domain Entity и Eloquent-моделей.
2. Меньше кода: не нужны Mapper-классы для преобразования между слоями.
3. Eloquent предоставляет достаточно абстрактный API и не создаёт критичной связанности с фреймворком.
4. Для большинства бизнес-задач это практичное решение.

### Когда это становится проблемой

- Нужна полная независимость от Laravel.
- Планируется миграция на другую ORM или БД.
- У сущности появляется сложная бизнес-логика, не связанная с персистентностью.

### Альтернатива: строгая Clean Architecture

Если требуется строгое соответствие Clean Architecture:

1. Создайте чистые Domain Entity без зависимости от фреймворка.
2. Разместите Eloquent-модели в `Infrastructure/Persistence`.
3. Добавьте Mapper для преобразования между Domain Entity и Eloquent-моделью.

Недостатки строгого подхода: больше boilerplate-кода, необходимость поддерживать синхронизацию двух представлений сущности и более высокая сложность для небольших проектов.

## Command и Query работают с БД напрямую

### Стандарт CQRS

Команды и запросы должны обращаться к данным через Repository-интерфейсы, определённые в Domain слое.

### Наше решение

Repository не используется для работы с БД. Command и Query обращаются к БД напрямую через `ConnectionInterface` и Query Builder.

```php
namespace App\Currency\Application\Query;

use Illuminate\Database\ConnectionInterface;

final readonly class GetExchangeRatesQuery
{
    public function __construct(
        private ConnectionInterface $manager,
    ) {
    }

    public function execute(string $baseCurrency): array
    {
        return $this->manager->table('exchange_rates')
            ->where('base_currency', $baseCurrency)
            ->get()
            ->toArray();
    }
}
```

### Почему принято это решение

1. ConnectionInterface и Query Builder предоставляют достаточно абстрактный API.
2. Уменьшается количество классов и интерфейсов.
3. Логика работы с данными остаётся простой и прозрачной.

## Упрощённая структура тестов

### Стандарт

Каждый компонент должен иметь соответствующий тест, а структура тестов должна полностью повторять структуру модуля.

### Наше решение

Не требуется создавать тесты для:

- Простых DTO без логики.
- Конфигурационных файлов.
- Простых исключений, наследующих базовые классы без дополнительной логики.

### Почему

1. Тесты простых DTO дают мало дополнительной ценности.
2. Команда концентрируется на тестировании бизнес-логики.
3. DTO покрываются в составе интеграционных тестов UseCase.

### Что обязательно тестировать

- Все компоненты Application слоя: UseCase, Command, Query, Service.
- Все компоненты Domain слоя с логикой: Entity, ValueObject с валидацией, Validation.
- Все компоненты Infrastructure слоя: Adapter для внешних систем.
- Все компоненты Presentation слоя: Controller, Listener, Console Command.

## Итог

Компромиссы уменьшают объём boilerplate-кода и ускоряют разработку, сохраняя разделение ответственности, тестируемость и расширяемость системы.

Если потребуется более строгое соответствие Clean Architecture, мигрируйте постепенно:

1. Выделите критичные модули.
2. Создайте для них чистые Domain Entity.
3. Добавьте Mapper-классы.
4. Постепенно перенесите остальные модули.

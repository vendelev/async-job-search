# Принятый в команде Code Style

## Импорты классов

Все полные наименования классов заменяйте на оператор `use` в начале файла.

```php
// Неправильно
$response = new \App\Task\Domain\Response\TaskResponse();

// Правильно
use App\Task\Domain\Response\TaskResponse;

$response = new TaskResponse();
```

Не добавляйте `use` для встроенных типов и функций PHP, а также классов из того же namespace.

## Оформление кода

### Тесты

Используйте статические вызовы PHPUnit: `self::assertTrue`, `self::assertFalse`, `self::assertSame`, `self::assertNull`, `self::assertEquals`.

### Код

- Максимальная длина строки -- 120 символов.
- Разбивайте длинные строки для читаемости.
- Не переопределяйте методы без изменения логики.
- После изменений проверяйте форматирование кода.
- Используйте типизированные константы для type safety.

### PHPDoc

- Добавляйте PHPDoc для всех public-методов.
- `@param` и `@return` добавляйте только для описания массивов.
- Документируйте исключения через `@throws`.
- Указывайте типы массивов в PHPDoc-комментариях для улучшения статического анализа.
- Для скалярных массивов используйте `list<...>` вместо `array<...>`.
- Когда гарантия обеспечена кодом, используйте уточнённые типы: `non-empty-string`, `positive-int`, `non-negative-int`, `non-empty-list<...>`.
- Не ужесточайте тип в PHPDoc без реальной гарантии от валидации, нормализации, ValueObject или бизнес-логики.
- Комментарии в коде пишите на русском языке; технические английские термины, имена классов, методов и переменных сохраняйте в исходном написании.

### Entity, DTO и интерфейсы

- Используйте публичные `readonly` свойства вместо геттеров, если дополнительная логика не требуется.
- Удаляйте лишние `@return void` из PHPDoc интерфейсов.
- Проверяйте корректность описаний методов.

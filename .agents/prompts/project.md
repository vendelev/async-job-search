# Архитектура проекта

## Design Patterns & Principles

1. **CQRS (Command Query Responsibility Segregation)**
2. **Clean Architecture**
   - Многослойная архитектура с четкими зависимостями
   - Доменно-ориентированное проектирование
   - Бизнес-логика, независимая от фреймворка
3. **Modular Monolith**
   - Независимые модули
   - Модульные API и контракты
   - Четкие границы модулей

Соблюдайте [стиль PHP-кода](snippets/CodeStyle.md). Справочник возможностей целевых версий языка: [PHP 8.4 и 8.5](snippets/PHP_8.4_8.5_Reference.md).

**Важно:** Для упрощения разработки приняты некоторые осознанные компромиссы относительно строгих правил Clean Architecture.
См. [Осознанные архитектурные компромиссы](snippets/ArchitecturalCompromises.md) для деталей и обоснования.

## Ключевые соглашения

- **Модуль**: Максимально самодостаточная часть продукта, отвечающая за определённый функционал. 
  Каждый модуль может содержать публичные доменные интерфейсы, сущности или события, определяющие границы его использования (API модуля).
- **UseCase**: Реализация конкретного варианта поведения пользователя (описывает, что пользователь хочет сделать).
- **DTO** (Data Transfer Object): Типизированная структура данных для передачи между слоями и модулями.
- **События** (Event): Специализированный DTO для информирования других модулей о произошедшем событии. Три типа:
  - **Уведомления** (Notification): DTO описывающий сообщение о завершённом действии в прошлом. Может быть синхронным или асинхронным. Много получателей возможно. Пример: *пациент был зарегистрирован*.
  - **Запросы** (Query): DTO описывающий синхронный запрос на получение данных. Ровно один получатель (один ответ). Пример: *получить историю пациента*.
  - **Команды** (Command): DTO описывающий синхронное указание другому модулю выполнить действие: создать, изменить или удалить данные. Ровно один получатель (одна обработка). Пример: *создать запись в журнале*.

## Структура директорий в модуле

### Application

Содержит реализацию бизнес-логики модуля:

- **UseCase**: Основной класс, реализующий вариант использования. Координирует работу Command, Query, Service.
- **Command**: Класс "команды" CQRS, реализующий логику изменения данных. Для упрощения реализации разрешается работать с БД напрямую.
- **Query**: Класс "запроса" CQRS, реализующий логику получения данных. Для упрощения реализации разрешается работать с БД напрямую.
- **Service**: Самодостаточная реализация специфичной логики, не зависящая от фреймворка.
- **Dto**: Объекты для передачи данных внутри Application слоя.
- **Factory**: Фабричные методы для создания DTO, Response, ValueObject.
- **Responder**: Генераторы специального контента вместо JSON: Excel, PDF, email. Содержит шаблоны и генераторы.

```text
Patient/
├── Application/
│   ├── UseCase/
│   ├── Command/
│   ├── Query/
│   ├── Service/
│   ├── Dto/
│   ├── Responder/
│   └── Factory/
```

### Domain

Предметная область и публичное API модуля. Все сущности отсюда доступны вне модуля:

- **{InterfaceName}.php**: Контракты для инверсии зависимостей и взаимодействия модулей.
- **Request** и **Response**: Immutable DTO входящих и исходящих данных.
- **Dto**: Immutable структуры для передачи между модулями и слоями.
- **Entity**: Описание структуры таблицы БД. Eloquent модели размещаются здесь как осознанный компромисс.
- **ValueObject**: Узкоспециализированный immutable DTO, иногда со встроенной валидацией.
- **Validation**: Классы для проверки бизнес-требований.
- **Event**: Immutable уведомления, запросы и команды для взаимодействия между модулями.
- **Exception**: Доменные исключения об ошибках в Application слое.
- **Doc**: Документация модуля и его API.

```text
Patient/
├── Domain/
│   ├── Doc/
│   ├── Dto/
│   ├── Request/
│   ├── Response/
│   ├── Entity/
│   ├── ValueObject/
│   ├── Validation/
│   ├── Event/
│   └── Exception/
```

### Infrastructure

Реализация интеграций с внешними системами (Anti-corruption layer):

- **Migration**: Список файлов с миграциями в БД.
- **Adapter**: Реализует Domain интерфейсы для работы с внешними сервисами и другими модулями.
- **{ServiceName}**: Адаптеры для взаимодействия с vendor-библиотеками.

```text
Patient/
└── Infrastructure/
    ├── Adapter/
    └── RamseyUuid/
```

### Presentation

Точка входа и выхода из модуля:

- **Http/Controller**: HTTP-контроллеры для обработки REST-запросов.
- **Http/Middleware**: Middleware-компоненты.
- **Http/View**: Рендеринг HTML-представлений и шаблоны.
- **Http/View/Template**: Нативные PHP-шаблоны для вывода HTML.
- **Console**: Крон-скрипты, демоны, консольные команды.
- **Listener**: Подписчики на доменные события.
- **Config**: Конфигурация модуля: environment, DI, service container, routing.

```text
Patient/
└── Presentation/
    ├── Http/
    │   ├── Controller/
    │   ├── Middleware/
    │   └── View/
    │       └── Template/
    ├── Console/
    ├── Listener/
    └── Config/
```

Это "максимальная" сложность одного модуля. Не требуется создавать все папки сразу.

## Структура директорий в проекте

- **backend**: реализация REST API и консольных команд.
  - **bootstrap**: файлы инициализации Laravel.
  - **config**: файлы конфигурации Laravel.
  - **database**: миграции и хранилище SQLite.
  - **src/Core**: ядро приложения, общепроектные события, исключения и обёртки над фреймворком и vendor. Структура аналогична модулю.
  - **src/{ModuleName}**: модули функциональности.
  - **tests/Architecture**: архитектурные тесты.
  - **tests/Suite/{ModuleName}**: тесты модуля.
  - **tests/Stub/ModelFactory**: генерация записей для тестирования.
- **docker**: файлы сборки Docker-контейнеров.
- **mock-server**: конфигурация HTTP mock server.

## Правила зависимостей между слоями

Каждый слой может использовать только свой и нижестоящие слои:

| Слой | Может использовать |
| --- | --- |
| **Presentation** | Infrastructure только своего модуля, Application только своего модуля, Domain своего и чужих модулей |
| **Infrastructure** | Application только своего модуля, Domain своего и чужих модулей |
| **Application** | Application только своего модуля, Domain предпочтительно только своего модуля |
| **Domain** | Domain своего и чужих модулей |

**Внедрение зависимостей (DI):**

- Не требуется создавать интерфейс, если существует одна реализация. 
- Не создавайте его «на будущее»: интерфейс оправдан, когда второй вариант уже существует или подтверждён требованием.
- Для использования Infrastructure-реализации в Application слое обязательно создайте интерфейс в Domain.

## Зависимости между модулями

Модуль должен быть максимально независим от других модулей, кроме `Core`.

Модули могут взаимодействовать двумя способами:

1. Синхронно через интерфейсы: модуль использует Domain-интерфейсы другого модуля через Adapter в Infrastructure.
2. Синхронно или асинхронно через события: модуль генерирует Domain Event, который обрабатывают Listener других модулей.

## Когда создавать интерфейсы

Интерфейс обязателен в следующих случаях:

1. В рамках модуля существует две или более реализаций функциональности.
2. Для инверсии зависимостей: Application слой зависит от Domain-интерфейса, который реализует Infrastructure.
3. Для взаимодействия модулей: при использовании функциональности другого модуля всегда через его Domain-интерфейс.

Интерфейс сам по себе не делает код расширяемым. 
Перед его созданием убедитесь, что есть реальная ось изменений: несколько вариантов поведения, которые будут развиваться независимо. 
Для единственного текущего сценария используйте конкретный класс и выделите контракт позже, когда появится второй вариант.

## Валидация и типизация

### На уровне Controller (Presentation)

Валидируются структурные характеристики данных: обязательность полей, типы и базовые форматы. 
Цель -- гарантировать, что из входящего запроса можно создать типизированный DTO.

### На уровне UseCase (Application)

Валидируются бизнес-требования: логические ограничения, состояния и доступность ресурсов. 
Используйте Validation-классы Domain либо проверки в UseCase или Service.

### Для сложных входных данных

Выносите парсинг и валидацию из Controller в Factory или Domain ValueObject.

### Типизация DTO

- В public и protected методах используйте типизированные DTO как параметры и возвращаемые значения.
- В private методах допускается использование ассоциативных массивов.

## Гранулярность ответственности в классе

### Оставлять методы в одном классе, если

- Зависимость из конструктора используется в нескольких методах для похожей функциональности.
- Методы отвечают за одну зону ответственности.
- Методы изменяются по запросам одного актора и по одной причине.

### Разделять на разные классы, если

- Части класса меняются независимо по запросам разных акторов или по разным бизнес-причинам.
- В одном классе накапливаются несколько подтверждённых вариантов поведения, и новый вариант регулярно меняет существующий код.
- Зависимость из конструктора используется в двух методах из пяти и более. Это только сигнал проверить ответственность, а не самостоятельная причина для нового класса.

Не делите класс только ради количества классов, методов или интерфейсов. 
До появления независимой причины изменения предпочитайте простую реализацию и рефакторинг по фактическому требованию.
